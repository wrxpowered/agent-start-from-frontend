## 单元 1：LLM 能力边界与可靠业务交互流程（已完成）

### 核心概念

- **LLM：** 根据上下文生成内容；输出可能合理但不真实，不能自动视为可信事实。
- **Token：** 模型处理文本的基本单位，不等同于单词或汉字。输入历史、系统指令、工具说明和输出都可能消耗 Token。
- **上下文窗口：** 单次模型调用可处理的信息容量，不是聊天记录的保存期限。长历史会增加消耗并可能淹没关键信息；摘要也可能遗漏关键业务状态。
- **Prompt 与消息角色：** 将任务指令、用户输入和输出约束清晰组织，减少指令与数据混淆。用户文本可能包含提示词注入，不能因此改变应用授权边界。
- **结构化输出：** JSON 便于程序处理，但格式正确不代表事实真实或业务合法。
- **运行时校验：** TypeScript 类型声明和 `as Type` 不会验证外部数据。使用 API 支持的结构化输出约束，并在应用侧用 Zod 等 Schema 校验实际响应。
- **分层校验：** Schema 校验数据形状；后端校验可信事实、身份、权限和业务规则；业务系统执行操作并记录结果。

### 售后 Agent 的职责边界

| 环节 | 主要职责 |
|---|---|
| LLM | 识别意图、提取商品问题、整理用户表达的主要与备用诉求 |
| Schema / runtime validation | 检查字段、类型、枚举和必需结构 |
| 后端 | 查询可信订单数据、验证订单归属、判断换货/退货/退款条件 |
| 业务系统 | 在校验和必要确认后执行操作，并记录实际结果 |

### 交互与异常处理

以“耳机右侧没有声音，优先换货，换不了则退款”为例：

1. 缺少订单号时，追问用户补充，或在可信登录身份下查询可用订单。
2. 查询失败时区分订单号错误、订单不存在与服务超时；不要把所有失败都当成订单不存在。
3. 订单归属校验失败时必须阻止操作，不能泄露他人订单信息。
4. 超过换货期限时，准确说明“已超过换货期限”，不要笼统称为“订单失效”。
5. 换货失败后独立检查退货/退款条件，不能默认退款必然可行。
6. 若有可行的退款方案，向用户说明条件并在流程要求时取得确认，再由后端执行。
7. 模型输出异常、业务条件不满足和系统故障是不同情况：分别考虑有限重试/错误返回、业务解释/替代方案、超时重试或降级。

### 验收结果

用户能用自己的话设计完整的售后处理流程：先补充订单标识，由后端查询并校验；再检查换货条件；不满足时检查退款条件；最后告知用户可选方案，并根据用户反馈继续推进。
