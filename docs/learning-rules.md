# 学习规则与工程原则

## 学习节奏与进度

- 按实际完成的学习单元和验收结果推进，不按日历天数推进。
- 不规定每次学习必须投入固定时长；按内容难度、连续性和学习效果安排。
- 中断后从上次实际进度继续，不因错过日期而自动跳过内容。
- 每个学习单元完成后统一复盘，再集中更新 GitHub 的全局进度、阶段笔记和必要文档；学习过程中不频繁同步。
- 未达到目标或验收标准时继续补充练习，不因计划日期而提前推进。
- 日常学习聚焦当前阶段；路线文档用于把握方向，不要求一次学习跨越多个阶段。

## 教学方式

- 默认采用“**代码示例 → 解释关键概念 → 分析工程问题 → 简短练习（必要时）**”。
- 用户有 Web 前端经验，优先使用 TypeScript 和熟悉的工程概念作切入点。
- 不等同于纯代码驱动：不要求一开始就编写完整项目；代码用于帮助理解概念，遇到问题时再补充必要原理。
- 避免冗长的纯概念讲解、重复解释和过度拆分的装饰性排版。
- 每次聚焦少量新概念，提供能说明问题的最小示例；练习以能检查实际理解为准，不用重复选择题凑时长。
- 对前端之外的后端、数据库、网络、命令行和部署概念，仍需在首次出现时解释清楚。
- 如果用户没理解，换一种讲法并用例子验证后再继续，不直接跳过。

## 总体学习路线

AI / LLM 基础与结构化交互 → 模型 API 与 TypeScript 后端 → RAG、检索与评估 → Tool Calling 与 Agent → MCP → 生产级 Agent 工程。

Python 作为按需能力模块穿插在主线中，不作为必须先完成的独立阶段。遇到 Python 专属工具或框架时，按项目需要集中补齐。详见 [Python 按需补充模块](../modules/python-on-demand.md)。

## 项目与评估原则

- 尽量围绕连续的业务场景迭代项目，避免每个主题都另起一个无关 Demo。
- 每个阶段都有明确交付物和可检查的验收标准。
- 从早期就建立测试样例；结构化输出、检索和 Agent 都要检查边界情况。
- “可以运行”不是充分的完成标准；要能解释为什么成功、如何发现失败、如何控制风险。
- 先理解核心机制，再按需求引入 SDK 或框架。
- 云端模型/API 优先，不把本地运行大型模型作为前置条件。

## 工程原则

- 模型负责理解、提取、分类和提出建议；可信业务事实应从后端或权威数据源获取。
- 后端负责鉴权、参数校验、业务规则、状态变更和最终结果确认。
- 对缺失信息要追问，对工具失败要有明确的错误处理与兜底流程。
- 工具调用遵循最小权限原则；执行有副作用的操作前应进行必要的验证与确认。
- 将模型输出视为不可信输入，使用 Schema、类型检查和业务校验约束输出。
- 项目成果应可运行、可测试、可解释、可复现；Demo 能运行不等于系统可靠。
